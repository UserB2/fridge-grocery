# 오늘의 냉장고 — 계정 로그인과 기기 간 동기화 설계안

작성일: 2026-11-04 · 상태: 사용자 ‘무료로만 되게 진행해줘’ 지시에 따라 무료 구성으로 구현 진행

## 승인된 변경 — 무료로만 운영

사용자는 비용 설명 후 ‘무료로만 되게 진행해줘’라고 지시했다. 이 조건에 맞춰 아래 원안의 이메일 인증코드를 **Google 로그인**으로 변경한다. Supabase Free와 기존 GitHub Pages를 사용하며, 이메일 발송 서비스·유료 요금제·결제 수단 등록·도메인 구매를 추가하지 않는다. 무료 한도 초과나 휴면 시 제한을 안내하고 자동 유료 전환하지 않는다. 아래 이메일 인증코드·발송 설정 설명은 대체된 원안이며 구현 기준은 이 변경 사항을 우선한다. 계정별 데이터 보존·이전·충돌 처리 요구는 유지한다.

## 원하는 결과

휴대폰과 컴퓨터에서 같은 이메일로 로그인하면 같은 냉장고·장보기·구매 내역을 사용한다. 현재 공개 주소와 기존 요리·장보기 기능을 유지하고, 브라우저에만 있던 기록도 계정으로 옮길 수 있게 한다.

웹사이트: https://userb2.github.io/fridge-grocery/

## 방식 비교와 선택 제안

| 방식 | 장점 | 필요한 작업 |
| --- | --- | --- |
| GitHub Pages 유지 + Supabase 이메일 인증코드·데이터베이스 | 기존 계획과 일치하고 현재 화면·배포를 유지할 수 있다. 비밀번호를 새로 만들 필요가 없다. | Supabase 프로젝트, 이메일 발송 설정, 계정별 저장·동기화 추가 |
| GitHub Pages 유지 + Firebase 인증·Firestore | 계정 인증과 실시간 데이터를 함께 제공한다. | 기존 Supabase 계획을 교체하고 별도의 저장 규칙·설정을 도입해야 한다. |

구현 담당자의 제안은 첫 번째 방식이다. 사용자가 요청한 결과를 현재 구조에서 구현하며, Supabase는 기존 기획서에도 후속 동기화 방법으로 명시되어 있다. 사용자가 이 문서를 승인하기 전까지 확정된 선택으로 간주하지 않는다.

## 화면과 사용 순서

1. 기존 프로필 메뉴에 ‘계정으로 로그인’을 추가한다.
2. 이메일을 입력하고 ‘인증코드 받기’를 누른다. 같은 화면에서 이메일로 받은 코드를 입력한다. 처음 사용하는 이메일은 인증에 성공하면 계정을 만든다.
3. 로그인 후에는 이메일과 ‘동기화 중 / 동기화 완료 / 연결 확인 필요’ 상태를 표시한다.
4. 다른 기기에서도 같은 이메일로 로그인하면 계정에 저장된 주방 목록을 불러온다.
5. 로그아웃하면 계정의 목록을 화면에서 숨기고, 해당 기기에 원래 있던 로컬 프로필로 돌아간다. 로그아웃은 계정의 서버 기록을 삭제하지 않는다.

화면 예시:

```text
계정으로 로그인
이메일 [                         ]
[인증코드 받기]

인증코드 [                      ]
[로그인]

로그인 후: 이메일 · 동기화 완료 · [로그아웃]
```

## 기존 기록 옮기기

- 현재 브라우저의 기존 저장 키를 그대로 보존하고, 계정 저장 공간과 분리한다.
- 계정 데이터가 없는 첫 로그인에서는 ‘기존 프로필 가져오기’와 ‘빈 주방으로 시작’을 제공한다. 사용자가 직접 고른 프로필만 업로드한다.
- 계정에 이미 목록이 있으면 우선 그 목록을 연다. 현재 기기의 로컬 목록을 자동 업로드하거나 계정 목록을 덮어쓰지 않는다.
- 기존 프로필을 나중에 가져오면 계정 안의 별도 주방으로 추가한다. 프로필 이름·항목 수를 미리 보여주며, 반복 클릭과 반복 가져오기로 같은 프로필이 중복 등록되지 않게 한다.
- 다른 브라우저에서 이미 내보낸 `fridge-grocery-profile` JSON 파일을 가져올 수 있게 한다. 형식과 필드를 확인하고, 잘못된 파일은 기존 데이터를 변경하지 않는다.
- 이전 방식으로 쓰고 싶은 사람은 로그인 없이 이 기기의 로컬 목록을 계속 사용할 수 있다.

## 동기화 동작

로그인한 상태에서 서버를 저장 기준으로 사용한다. 추가·수정·구매 기록 저장은 서버의 저장 성공을 확인한 뒤 완료로 표시한다. 구매 기록 생성과 냉장고 등록은 기존처럼 한 번의 상태 변경으로 처리한다.

다른 기기의 변경은 실시간 구독으로 받고, 앱을 다시 열거나 화면으로 돌아올 때도 서버에서 확인한다. 실시간 연결이 끊겨도 열린 화면에서는 30초 간격으로 재확인한다. 백그라운드에 오래 머문 모바일 브라우저의 즉시 반영은 보장하지 않으며, 화면 복귀 시 최신값을 가져온다.

기기 두 대가 같은 버전에서 동시에 수정하면 서버는 먼저 저장된 변경만 승인한다. 나중 변경은 조용히 덮어쓰지 않고 ‘다른 기기에서 목록이 바뀌었어요’를 표시한다. 현재 입력을 파일로 보관하거나 복사할 수 있게 한 뒤 최신 기록을 다시 불러온다. 자동으로 두 변경을 합치거나 마지막 기기의 기록으로 덮어쓰지 않는다.

편집 창이나 저장하지 않은 가격 입력이 열려 있으면 원격 변경으로 화면을 다시 그리지 않는다. 변경 알림을 표시하고 입력 내용을 보존하며, 저장 시 버전 충돌 여부를 검사한다. 서버 요청 도중 중복 저장 버튼을 막고, 응답이 불명확하면 최신 버전과 마지막 저장 식별자를 조회하여 실제 저장 여부를 확인한다.

인터넷이 끊기면 마지막으로 받은 계정 기록을 볼 수 있지만, 새 변경은 연결이 복구될 때까지 저장하지 못하게 안내한다. 오프라인 변경 대기열과 자동 병합은 이번 범위에 포함하지 않는다.

## 계정 구분과 저장 구조

- 계정마다 기존 버전 1 상태 모양을 담은 하나의 저장 문서와 서버 관리 버전 번호를 둔다. 냉장고·장보기·구매 기록·추천·계정 내 주방 프로필이 포함된다.
- 계정의 여러 주방 프로필은 같은 계정 안의 분류다. 다른 이메일 계정에서는 접근할 수 없다. 가족 간 서로 다른 계정의 공동 편집과 초대는 이번 범위에 포함하지 않는다.
- 현재 선택한 화면·검색 조건·활성 주방은 기기별 화면 설정으로 두어 다른 기기의 조작을 바꾸지 않는다.
- 서버는 인증된 사용자 ID로 소유자를 결정한다. 브라우저가 보낸 이메일이나 다른 사용자 ID를 접근 권한으로 신뢰하지 않는다.
- 데이터베이스의 행 단위 접근 제어로 본인 데이터만 읽고 쓸 수 있게 한다. 저장 함수도 사용자 ID·기대 버전·상태 형식·요청 크기를 확인하고 한 번에 변경한다.
- 공개 웹 코드에는 프로젝트 주소와 공개용 키만 포함한다. 관리자 키, 데이터베이스 비밀번호, 이메일 발송 비밀키는 넣지 않는다.
- 계정 캐시는 사용자 ID별로 분리하며 로그아웃 시 계정 캐시를 제거한다. 로그아웃·계정 변경 뒤 도착한 이전 요청 응답은 화면이나 새 계정 데이터에 반영하지 않는다.

## 필요한 서비스 설정

Supabase 프로젝트에 인증, 계정별 데이터 테이블, 저장 함수, 접근 규칙, 실시간 변경 전달을 설정한다. 이메일 템플릿은 로그인 링크 대신 코드를 표시하도록 설정한다. 사이트 주소는 현재 GitHub Pages 주소를 사용한다.

일반 사용자의 이메일로 코드를 보내려면 발송 서비스 연결이 필요하다. Supabase 기본 발송은 팀에 등록한 이메일을 대상으로 하는 테스트용이므로 실제 사용자 로그인 완료로 간주하지 않는다. 사용할 Supabase 프로젝트와 발송 계정의 소유자 인증은 사용자가 관리 화면에서 직접 처리한다. 비밀키를 이 문서나 채팅에 붙여넣을 필요는 없다.

현재 세션에서 Supabase 연결 도구는 사용할 수 없는 상태다. 설정 시 관리 화면을 이용하고, 접근할 수 없는 설정만 사용자에게 구체적으로 안내한다. 기능을 만들고 검증하기 전에 운영 사이트를 미완성 로그인 화면으로 교체하지 않는다.

## 완료 확인 기준

1. 실제 이메일로 받은 코드로 가입·로그인·재로그인·로그아웃이 된다. 잘못된 코드, 만료, 재발송 제한도 안내한다.
2. 서로 다른 브라우저 두 개에서 같은 계정으로 로그인한 뒤, 재료·장보기·가격·구매 기록·냉장고 등록 변경이 서로 반영된다.
3. 서로 다른 두 계정으로 상대 데이터의 읽기·생성·수정·삭제가 모두 거부되는지 실제 데이터베이스 권한으로 확인한다.
4. 기존 로컬 프로필과 내보내기 파일을 가져온 뒤 품목·금액·구매품 등록 여부를 보존하고 중복 가져오기를 막는다.
5. 동시 수정, 응답 유실, 연결 끊김, 세션 만료, 계정 전환 중의 지연 응답에서 덮어쓰기와 계정 간 혼합이 생기지 않는다.
6. 기존 자동 테스트 26개와 새 인증·저장·동기화 검증을 통과하고 모바일 화면을 확인한다.
7. 운영 주소에 배포한 뒤 로그인과 두 기기 동기화를 다시 확인한다. 확인하지 못한 외부 서비스 조건은 완료로 표시하지 않는다.

## 구현 담당자가 정할 세부 사항

Supabase JavaScript SDK의 고정 버전과 배포 방식, 파일 분리, 구체적인 테이블·함수 이름, 입력 안내 문구와 화면 간격은 구현 단계에서 정한다. 새 프레임워크로 전체 사이트를 다시 만들지 않고 기존 HTML·CSS·JavaScript 구조를 유지한다.
